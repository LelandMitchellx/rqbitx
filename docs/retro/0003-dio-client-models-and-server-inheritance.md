# Retro 0003: Dio 客户端、1:1 模型映射、单实例继承与全景台账复盘

> **审查阶段**：Dio 客户端演进、官方 API 全量补齐、单实例继承重构与生产就绪安全审计（对应 PRD-0002、ADR-0007 ~ ADR-0009）  
> **复盘目标**：反思 API 消费体感割裂、信息沉淀断层与安全审查盲区。

---

## 一、会话摩擦点与踩坑事实回顾 (What Went Wrong)

1. **摩擦点 1：双实例（Server + Client）设计带来的人机协同认知负荷**
   - **现象**：初期为了追求“关注点分离”，将 `RqbitServer`（仅负责 FFI 启停）与 `RqbitClient`（负责 Dio HTTP 调用）彻底拆成两个平行的类。这导致在 UI 层必须维护 `_server` 和 `_client` 两个变量；在退出时需要先手动关 client 连接池再停 server；调用方需要反复判断到底向谁发起请求。
   - **根本原因**：过度将架构解耦推向极端，忽视了“深模块（Deep Module）”原则——外部调用方只关心“我拥有一个 rqbit 节点，我既能启停它，也能直接调用它的下载 API”。

2. **摩擦点 2：高密度演化缺乏集中台账导致用户产生失控感**
   - **现象**：在连续完成 11 个阶段的复杂迭代后，用户反馈：“*现在一个整个项目下来我已经不知道改了什么了，我的想法是，一开始最初有最根本的一个需求，后面的 BUG，提案都要有修改记录*”。
   - **根本原因**：虽然每次改动都写了 ADR、更新了 spec，但缺乏一份按时间倒序/演进脉络整合的**唯一事实来源（Single Source of Truth）全景变更日志**。人类开发者在面对大量自动化代码吞吐时，无法快速掌握全貌。

3. **摩擦点 3：生产就绪度安全盲区在开发早期被长期忽视**
   - **现象**：直到主动引入 Reviewer 子 Agent 进行生产就绪审计时，才猛然发现多处致命 P0 缺陷：Android 清单未配置 `INTERNET` 权限、本地 127.0.0.1 HTTP 服务零鉴权（易遭网页恶意 CSRF 攻击）、Rust 默认版本使用了未稳定的 1.98 通道。
   - **根本原因**：日常会话过于聚焦在“把功能跑通、测试全绿”，缺少专门的“安全与平台清单强制审查项”。

## 二、环境改进候选方案 (Environment Improvements)

### 1. 核心制度与台账（Process & Ledger）
- **全景演进台账制度**：
  - 强制在根目录建立并维护 `CHANGELOG.md`；
  - 铁律：**任何后续新需求（Enhancement）、缺陷修复（Bug）或架构优化，提交代码前必须同步在 CHANGELOG.md 追加记录**，写明根本原因、改动内容与影响面。

### 2. 代码审查准则 (Reviewer Coding Standards)
- **单实例深模块准则**（沉淀入 `CODING_STANDARDS.md`）：
  - 统一由 `RqbitServer extends RqbitClient` 暴露给消费层，确保单一实例兼具生命周期与所有业务 API；
  - 资源生命周期联动：`server.stop()` 必须自动级联关闭底层 HTTP Client 连接池，禁止要求调用方手动双重释放。
- **1:1 领域模型保真准则**：
  - 所有 Dart DTO 必须与 Rust 数据结构 1:1 镜像，明确区分可选字段（`?`），反序列化杜绝裸 `as` 类型强转。
- **安全基线审查清单**：
  - 移动端发布必须显式核对 Android 清单文件权限（网络、存储沙盒）；
  - 守护进程监听必须考量本地无鉴权防护（如生成临时随机 Token）。

### 3. 导航指针 (Navigation Pointers)
- **改进措施**：
  - 在 `AGENTS.md` 顶层增加指向 `CHANGELOG.md` 和 `CODING_STANDARDS.md` 的永久导航指针。
